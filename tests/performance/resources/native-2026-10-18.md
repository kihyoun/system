# Native platform and CI capacity evidence, 2026-10-18

This report advances [System #26](https://github.com/kihyoun/system/issues/26).
Retain the existing **8 dedicated vCPU / 32 GB class** host for the complete
platform and isolated-recovery workflow, with **one heavy workload at a time**.
The highest sampled host use is already **16.93 GiB** during a diagnostic
candidate run. A 16 GB host would leave no credible reserve for that workload.
This is an operating recommendation for the measured setup, not evidence that
all planned workloads or long-term retention are qualified.

The initial persistent-volume constraint has been resolved: after observing
**81% used / 1.76 GiB available** on the old 10-GB-class volume, the maintainer
expanded the existing device to **25 GiB**, and the coordinator grew the same
ext4 filesystem online. It now has approximately **24.5 GiB capacity / 15.75 GiB
available, 33% used**. The measurement worker performed no resize, deletion,
global prune or production restart. Controlled template builds ran only during
an explicit coordinator lease; backup and rollback state remain protected.

## Inventory and accounting

The native Hetzner x86_64 VM exposes eight logical CPUs, 32,852,004,864 bytes
(30.60 GiB) of usable Linux RAM, no swap, Docker 29.9.1 and cgroup v2. These
observations are from the Linux VM, independently of the earlier Windows/WSL
incident. The collector labels virtualization `linux-unclassified`; the operator
identifies the platform as the native Linux cloud VM.

Five platform containers run GitLab (including registry/database), the runner
manager, NGINX, Wizard and controller (including Sync). Their initial complete
background observation attributes 5.73 GiB Docker working set to GitLab, about
52 MiB to the controller, 18 MiB to the runner, 11 MiB to NGINX and 7 MiB to the
Wizard. GitLab later reaches at least 8.03 GiB observed working set. Embedded
registry/database and Sync cannot be independently attributed from container
totals. The three-sample baseline is background activity, not a verified quiet
or idle benchmark.

Host use is `MemTotal - MemAvailable`. Docker Linux working set subtracts cache;
`memory.current` includes it. Do not add either container totals or separate
role maxima to host usage. For example, the modern Wizard BuildKit worker has
an observed 0.76 GiB Docker working set but 3.52 GiB cgroup usage including cache.
That difference is accounting, not an additional allocation. Cgroup lifetime
peaks may predate a window. Missing role measurements remain null; individual
observed values are lower bounds, not replacements for missing samples.
For Docker-in-Docker, a PID-mapped cgroup can describe a descendant subgroup:
its reported peak and the Docker aggregate are not interchangeable whole-daemon
peaks. For example, the original System33 private daemon shows about 8.45 GiB
Docker working set but 7.14 GiB from the PID-mapped cgroup peak. The declared
12-GiB limit comes independently from Docker configuration.

## Storage and retention

Before expansion, at 10:49 UTC, root had 207,356,968,960 bytes available and the persistent volume
had 1,886,892,032 bytes available. A subsequent bounded read-only category scan
found approximately 0.89 GiB live GitLab data, 0.84 GiB current Seed and 5.74 GiB
retained backups, with small TLS/configuration/runner-identity directories.
These categories explain most of the volume's 7.47 GiB used space; the backup
category is all protected retained backups, not only one historical Seed.

The maintainer subsequently expanded the existing device to 26,843,545,600 bytes
(25 GiB). The coordinator completed a guarded online `resize2fs` on the same
ext4 filesystem and mount, preserving UUID `07e22857-8272-430d-bd3f-8fcd02c6d9ca`.
Verified post-expansion filesystem bytes: capacity 26,309,095,424; used
8,183,861,248; available 16,905,883,648 (33% used). No Seed, protected backup or
rollback image was removed to obtain this capacity. Filesystem reservation
means capacity minus used need not equal non-root available bytes.

During pipeline24, root availability fell from 193.62 to 185.72 GiB, then
recovered after owned candidate cleanup. That is an observed transient 7.89 GiB
window change, not a retained-data growth rate. A later Docker snapshot reports
14.3 GB images, 4.02 GB build cache and 1.92 GB local volumes; these categories
can share layers or include bind-backed state and must not be added to `df`.
No multi-day image/artifact/registry growth rate has yet been measured.

Recommended policy, to implement only after operator review:

- Keep the active promoted immutable image, its previous rollback image and
  matching provenance/checkpoints exempt from cleanup. Keep the old Seed backup.
- Continue job-owned builder/container/tag cleanup. Never replace it with a
  global Docker prune or delete named volumes merely marked reclaimable.
- Keep required CI evidence for at least the current recipe's seven-day artifact
  period. Define per-project registry retention and a build-cache budget;
  measure their growth before extending retention.
- Maintain at least 25% usable free capacity and at least one complete additional
  harvest/export plus 2 GiB transient reserve on the persistent volume. The
  original 1.76 GiB free failed even the fixed reserve. The completed 25-GiB device
  expansion now accommodates current retained data and an initial 5-GiB CI growth
  budget with reserve. That is an explicit budget, not a measured long-term rate;
  continue to measure growth instead of assuming the expansion removes retention needs.
- Keep at least 40 GiB root space available before a full disposable candidate;
  record before/after storage and refuse overlapping heavy jobs while this
  reserve or the persistent-volume reserve is breached.

Use `required usable bytes >= (live + active Seed + protected backups + retained
CI/registry budget + largest harvest/export staging + growth allowance) / 0.75`.
Root disk headroom cannot substitute for the externally retained volume.

## Sizing and concurrency decision

Official specifications and June-2026 price table were checked on 2026-10-18.
Prices below are Germany/Finland monthly caps, excluding VAT, IPv4, volume,
backups and other extras; availability and checkout pricing require a fresh
check before any purchase. The public catalog displayed unavailable entries,
so this table is a comparison, not an availability promise.

| --- | ---: | --- | ---: | --- |
| CCX13 | 2 dedicated | 8 GB / 80 GB | 42.99 | Insufficient for measured GitLab plus full CI |
| CCX23 | 4 dedicated | 16 GB / 160 GB | 85.99 | Unqualified reduced-workload option; full candidate reserve inadequate |
| CCX33 | 8 dedicated | 32 GB / 240 GB | 138.49 | Recommended measured-host class, one full candidate at a time |
| CX43 | 8 shared | 16 GB / 160 GB | 15.99 | Same RAM concern; shared-CPU transfer unmeasured |
| CX53 | 16 shared | 32 GB / 320 GB | 29.49 | Lower-cost comparison; CPU contention and availability unqualified |

Sources: [dedicated specifications](https://www.hetzner.com/cloud/general-purpose/),
[shared specifications](https://www.hetzner.com/cloud/cost-optimized/),
[official pricing](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/).

The minimum recommended class for the **complete current workflow** is 32 GB.
A 16 GB service-plus-one-small-build configuration remains a narrower hypothesis,
requiring its own capped workload test; it must exclude the 12-GiB private
GitLab candidate. Do not describe it as a validated minimum. Use this operating
budget on the current 30.60-GiB-usable host: approximately 10 GiB service reserve,
12 GiB maximum one private candidate, 0.5 GiB driver and 4 GiB OS/transient reserve.
Do not admit a second full candidate; two such 12-GiB candidates exceed that
budget. Ordinary template/Wizard builders are capped at 4 GiB/two CPUs and run
separately from that heavy lane until overlap is measured.

Long queue time with spare sampled CPU suggests testing controlled concurrency
before purchasing CPU. A second runner manager without another execution slot
or host capacity cannot increase throughput. Add a separate runner host when
more simultaneous heavy candidates are required, or sustained ordinary-build
queue time exceeds execution time after bounded concurrency is measured.
Increase RAM or move builds when repeated successful runs breach a 25% RAM
reserve, introduce swap/OOM pressure, or cannot fit their declared limits.
Increase dedicated CPU when controlled runs repeatedly sustain over 80% total
CPU and build duration worsens with overlap; the current samples do not show it.
Increase storage when the stated reserve or retention-growth forecast is breached.
